# 从软件转发到硬件转发

> **一次星载载荷数据面下沉的完整工程实践**
>
> 本文回答一个问题：如何把一个"靠 CPU 搬运样点"的软件转发器，改造成"数据永远不离开芯片"的硬件弯管转发器。
> 重点不在具体代码，而在**判断依据、路线选择与实施方法**。

---

## 摘要

改造前，系统的转发吞吐被压在 **2.92 MSPS**，占空比仅 **9.5%**，端到端时延 **>17 ms**，且**必须有一台主机在线**才能工作。

改造后，吞吐达到 **30.72 MSPS**（10.5 倍），占空比接近 100%，数据面时延降到 **81 ns**（约 21 万倍），**上电即工作**，主机只负责写几个配置寄存器。

关键认识是：**瓶颈不在代码效率，而在物理路径。** 所有数据必须绕行「DDR → Linux → USB → 主机 → USB → DDR」这一圈，而 USB 2.0 的实测可用带宽只有约 35 MB/s，而这条链路的需求是 **245.76 MB/s**。

因此这不是"优化"，而是"改道"——把数据面从主机侧整体下沉到 FPGA 内部。

---

## 一、改造前：软件转发器的真实形态

### 1.1 系统构成

```
┌─────────────────┐   USB 2.0    ┌──────────────────────────────┐
│  RK3588 主机     │◄────────────►│  LDSDR (Zynq XC7Z010+AD9361) │
│  4×A76 + 4×A55  │              │  固件: ADI Pluto 兼容         │
│  Python + NumPy │              │  含 axi_ad9361 + axi_dmac     │
└─────────────────┘              └──────────────────────────────┘
```

### 1.2 数据流路径

每一次"转发一个样点"，数据要走完这一整圈：

```
AD9361 ──LVDS──► PL(axi_ad9361) ──► axi_dmac ──► DDR
                                                  │
                                            Linux 内核缓冲
                                                  │
                                                 USB  ──► RK3588
                                                  │
                                          Python: iq = sdr.rx()
                                                  │
                                            NumPy 处理
                                                  │
                                          Python: sdr.tx(iq)
                                                  │
                                                 USB  ──► DDR
                                                  │
                                       axi_dmac ──► PL ──LVDS──► AD9361
```

**样点被搬运了 6 次，跨越 4 个时钟域、2 个操作系统边界。**

### 1.3 实测性能

| 指标 | 实测值 |
|---|---|
| 转发吞吐 | **2.92 MSPS** |
| 链路占空比 | **9.5 %** |
| 块时延 | **8.53 ms**（`BUF_SIZE = 2¹⁸` @30.72 MSPS） |
| 主机依赖 | 必须在线 |

## 二、瓶颈的物理本质

### 2.1 带宽账

```
需求（单向下行或上行）：
   30.72 MSPS × 2(I/Q) × 2 Byte = 122.88 MB/s

需求（收发合计）：
   122.88 × 2 = 245.76 MB/s

供给（USB 2.0 High-Speed，实测）：
   ≈ 35 MB/s
```

**理论可达速率：**

```
35 / 245.76 × 30.72 = 4.37 MSPS
```

**实测 2.92 MSPS，是理论值的 66.7%** —— 剩下的 33% 被 Linux 调度抖动与 Python/NumPy 的解释开销吃掉。

**结论：即使把 Python 换成 C、把 NumPy 换成手写 SIMD，上限也只有 4.37 MSPS。这是 USB 2.0 的物理上限，不是软件问题。**

### 2.2 时延账

| 环节 | 时延 |
|---|---|
| RX 缓冲累积（`2¹⁸` 样点） | 8.53 ms |
| USB 往返 + 内核调度 + Python | 数 ms 量级 |
| TX 缓冲累积 | 8.53 ms |
| **端到端合计** | **> 17 ms** |

对于 LEO 卫星（星地单向传播时延约 2~7 ms），**转发器自身引入 17 ms 以上的时延是不可接受的** —— 它会直接吃掉链路预算里的时延余量。

更何况：**块时延与块大小成正比，而块越小、USB 开销占比越高、效率越低。** 这是一个无法两全的死结。

### 2.3 架构账

| 维度 | 软件转发 | 后果 |
|---|---|---|
| 主机依赖 | 必须有主机在线 | 主机断电 = 转发电中断 |
| 确定性 | Linux 非实时调度 | 偶发丢样，不可承诺 |
| 功耗 | 主机 + SDR 双份 | 星上不可接受 |
| 可复现性 | 依赖主机软件栈版本 | 不可审计 |

**对星载载荷而言，最致命的是"确定性"和"主机依赖"这两条。**

### 2.4 把账算清之后的结论

```
这不是"代码跑得慢"，是"数据走错了路"。
```

任何在主机侧的优化都改变不了 245.76 MB/s 的需求撞上 35 MB/s 的供给这个事实。
**唯一的出路是让数据不再走那条路。**

## 三、技术路线选择

摆在我们面前有三条路：

| 路线 | 做法 | 优点 | 缺点 | 结论 |
|---|---|---|---|---|
| **A** | 在板卡厂商提供的裸机工程上，把转发数据面直接做进 PL 内部闭环 | 插入点极干净；上电即工作；风险低；最符合星载载荷形态 | 失去 IIO/USB 的调试便利 | ✅ **采用** |
| **B** | 从 ADI 开源仓库取 `hdl` 重建带 DMA 的参考设计，在 AXIS 通路上插自研 IP | 保留 DMA + Linux + IIO | 版本匹配、引脚约束、device-tree 三重坑；工程量大；仍然绕不开主机搬运 | ❌ 暂不采用 |
| **C** | 继续优化主机侧软件（C 重写、零拷贝、批量传输） | 改动小 | **受限于 USB 物理上限，天花板只有 4.37 MSPS** | ❌ 不可行 |

### 选 A 的决定性依据

对厂商裸机工程做完整核查后，发现了一个**出乎意料干净的插入点**：

```verilog
// ad9361_phy 暴露的接口
output        data_clk,                          // 全局数据时钟
output [11:0] adc_data_d1, adc_data_q1,          // RX1 I/Q
output        adc_d1q1_valid,
input  [11:0] dac_data_d1, dac_data_q1,          // TX1 I/Q
input         dac_valid
```

**收发在同一时钟域（`data_clk`），中间没有任何跨时钟域。**

于是整个弯管转发的核心只需要三行：

```verilog
assign dac_data_d1 = adc_data_d1;
assign dac_data_q1 = adc_data_q1;
assign dac_valid   = adc_d1q1_valid;
```

**"三行直通"就是硬转发的最小可行产品。** 这个事实让路线 A 的风险从"高"降到了"中"——因为第一步可以小到几乎不可能失败。

## 四、改造的五个阶段

### 阶段一：把黑盒变成白盒

**目标：在动手之前，先确知每一根线的来龙去脉。**

核查手段（全部基于实际文件，不靠推测）：

| 对象 | 手段 | 得到的结论 |
|---|---|---|
| `design_1.bd` | 解析 JSON，列出全部 IP、端口、网表 | **没有 DMA、没有 AXIS、ADC 只接到 ILA、TX 由 DDS 驱动** |
| `ad9361_phy.v` | 读端口列表 | 收发的 IQ 并行口，同时钟域 |
| `phy_rx.v` / `phy_tx.v` | 读 valid 生成逻辑 | `dac_valid` 是**启动脉冲**不是每样点使能；2R2T 下 `data_clk = 4 × 采样率` |
| `axi_ctrl_v1_0.v` + `component.xml` | 读端口与寄存器映射 | 16 个寄存器槽只用了 4 个 |
| `config.h` + `main.c` | 读裸机工程 | `AXI_ADC_NOT_PRESENT`；初始化后 `while(1)`，无运行时接口 |
| UG-570（128 页） | 查 Rx/Tx 信号链 | ADC_CLK 高达 245.76 MHz，片内已四级抽取；片内已有 128 抽头 FIR |

**这一阶段推翻了三个初始假设：**

1. ~~"PL 在做信号处理"~~ → PL 是纯直通/搬运
2. ~~"手上的工程就是板子在跑的固件"~~ → **是两个完全不同的设计**（手上是裸机 demo，板上跑的是 ADI 参考设计）
3. ~~"简介里的 PL DDC/DUC 已经在做了"~~ → 一行自研 RTL 都没有

> **方法要点**：不要相信文档和注释，去读 `.bd` 的 JSON、读 RTL 源码、读手册原文。
> 上面的每一条结论都有明确的文件与行号出处。

### 阶段二：定义接口契约

**目标：把"插入点"变成一份可以写进代码的契约。**

契约定为：

| 方向 | 信号 | 含义 |
|---|---|---|
| 输入 | `adc_data_d1/q1` + `adc_d1q1_valid` | 12 bit 有符号，满幅 ±2047 |
| 输出 | `dac_data_d1/q1` + `dac_valid` | 同上 |
| 时钟 | `data_clk` | **收发同一域，数据通路内零 CDC** |
| 控制 | AXI-Lite | 5 个控制字（模式/DDC 频率/DUC 频率/增益/隔直） |
| 状态 | AXI-Lite | 3 个只读计数器（收/发/饱和） |

**"收发同一时钟域"是这份契约里最值钱的一条** —— 它把整个设计里最容易出问题的部分（跨时钟域）直接消掉了。

同时确定了一个**关键的架构定位**：

> PL 的 DDC 不是"第一级下变频"，而是**第二级**。
> 第一级是 AD9361 片内的模拟混频 + 四级数字抽取/内插。
> PL 拿不到原始 ADC 数据（ADC_CLK 245.76 MHz vs 接口上限 61.44 MSPS）。

这个定位决定了 PL 该做什么、不该做什么：

| PL 该做 | PL 不该做 |
|---|---|
| 频偏/多普勒的连续相位快速补偿 | 重复实现片内已有的 128 抽头 FIR |
| 多信道并行信道化 | 试图"从 ADC 裸数据开始" |
| 数据率压缩 | — |

### 阶段三：数据面下沉（PL）

**实施顺序（每一级都可独立验证、可回退）：**

| 级 | 内容 | 验证方式 |
|---|---|---|
| 0 | **三行直通**（ADC→DAC 直连） | 综测仪看到转发信号 = 通路打开 |
| 1 | 加 AXI-Lite 寄存器 | PS 写、读回 |
| 2 | 加 DDC 复混频 + DUC 复混频 | 单音搬频可观测 |
| 3 | 加隔直器 | 中心杂散消失 |
| 4 | 加数字增益 | 幅度可调 |

**为什么第 0 级必须是"三行直通"**：

- 它的技术含量最低，但**它能回答整个项目最大的不确定性**——"我到底能不能改这块板子的 PL，而且它还能正常起来"
- 在它跑通之前，任何 DSP 设计都可能白做
- 它把"改 PL"这件事从"高风险赌博"变成"已验证的能力"

**数据面的核心设计决策：**

| 决策 | 依据 |
|---|---|
| 收发共用一组控制字，DDC 与 DUC 各自独立的 NCO | 净变换 = DUC − DDC，一个公式覆盖所有场景 |
| 32 位相位累加器 | 频率分辨率 fs/2³² ≈ **7.2 mHz** @30.72 MSPS，远超 RF LO 的调谐精度 |
| 隔直器用泄漏积分器而非 IIR 乘法器 | **0 个 DSP48** |
| 双通道并行（ch1→TX1, ch2→TX2） | AD9361 有 2RX/2TX，不用的通道会输出直流 |
| 四种模式延迟全部一致 | 软件切换模式不改变 DAC 时序 |
| 流水线由时序倒逼加深到 **9 级** | 见下 |

**流水线为什么是 9 级而不是 3 级：**

最初的设计只有 3 级，关键路径是

```
ROM → 象限取反(CARRY4×3) → LUT → DSP48乘 → DSP级联加 → 饱和比较 → 寄存器
数据路径 12.03 ns
```

时序无法收敛。修复分三步：
1. 复混频器拆成两级（乘积寄存 / 加法+饱和寄存）
2. NCO 输出加一级寄存（切断 `BRAM → 取反 → DSP`）
3. 旁路选择结果寄存（切断宽扇出控制网进入隔直进位链）

**这不是"为了深度而深度"，而是"每级都必须短到能满足建立时间"。**

### 阶段四：控制面重建（PS）

**目标：让 PS 从数据面彻底退出，只保留配置与监测。**

| 原状态 | 改造后 |
|---|---|
| 初始化后在 `while(1)` 空转 | 初始化 → 写转发参数 → **健康自检** → UART 命令行 |
| 无运行时接口，改一个参数要重编译 | 约 40 条串口命令，参数实时可改 |
| 无状态可见性 | 三个计数器 + 串口状态行 + JTAG 信箱，三条独立观测通道 |
| 无安全机制 | 上电默认静音；自检失败自动静音 |

**PS 侧必须修掉的三个硬伤（都是上电前必须处理的）：**

| 项 | 原值 | 问题 | 修正 |
|---|---|---|---|
| AD9361 BIST | `0x3F4 = 0x03` | = BIST 使能 + TX 注入点 + 单音模式，**芯片内部单音会取代接口送来的 DAC 数据，转发信号根本发不出去** | 关闭 |
| TX 衰减 | `70` | 驱动文档明确单位是 **mdB**，`70` mdB = 0.07 dB ≈ **满功率** | 改 `30000`（30 dB） |
| 收发频点 | 2400 / 2400 MHz | 同频，FDD 下易自激 | 改 900 / 1000 MHz |

### 阶段五：建立"可证伪"的验证体系

**这是整个改造里最容易被忽视、却最关键的一步。**

改造前验证转发靠的是"看频谱对不对"——**主观、不可量化、无法证明没有丢样**。

改造后建立了三层验证：

| 层 | 手段 | 证明了什么 |
|---|---|---|
| **仿真** | ModelSim + 整周期 FFT 分析，12 项断言 | 功能正确性、频率精度、饱和行为、2R2T 稀疏时序 |
| **计数器** | PL 内两个计数器 + 快照跨域 | **零丢样**（Δin ≡ Δout）、无饱和 |
| **仪器** | CMU200 频谱 | 端到端射频正确性 |

**其中"计数器比对"是最有价值的一条。** 它的判据是：

> 在一段稳定时间内，`ΔSAMPLE_CNT` 必须**逐位等于** `ΔOUT_CNT`。

实测结果：

```
read 1 : in=1,186,590,702  out=1,186,590,714  clip=275,615  rc=0
read 2 : in=1,264,861,166  out=1,264,861,178  clip=275,615  rc=0
         Δin = 78,270,464   Δout = 78,270,464     ← 完全相同
read 3 : in=1,343,057,902  out=1,343,057,914  clip=275,615  rc=0
         Δin = 78,196,736   Δout = 78,196,736     ← 完全相同
```

**这个方法的三个优点：**
1. **不依赖仪器** —— 纯数字证据
2. **可自动化** —— 一条 Tcl 脚本跑三轮即可
3. **可证伪** —— 只要丢一个样点，增量立刻不等

配套的设计（现在写进了 RTL）：

```verilog
// 计数器在数据域，用影子寄存器 + 翻转握手跨到 AXI 域
// 保证读到的永远是同一时刻的自洽快照，不会撕裂
relay_counter_snap u_snap (
    .dclk(dq_data_clk), .dclk_inc(adc_d1q1_valid),
    .cnt_a(sample_cnt), .cnt_b(clip_cnt), .cnt_c(out_cnt),
    .raxi_clk(raxi_clk), .out_a(...), .out_b(...), .out_c(...)
);
```

## 五、改造前后对比

| 维度 | 改造前（软件转发） | 改造后（硬件转发） | 改善 |
|---|---|---|---|
| **转发速率** | 2.92 MSPS | **30.72 MSPS** | **10.5 ×** |
| **链路占空比** | 9.5 % | ≈ 100 % | **10.5 ×** |
| **数据面时延** | > 17 ms（端到端） | **81 ns**（10 个 `data_clk` 周期） | **~21 万 ×** |
| **数据搬移次数** | 6 次（跨 4 个时钟域、2 个 OS 边界） | **0 次**（不离开芯片） | — |
| **主机依赖** | 必须在线，断电即中断 | **上电即工作** | 架构级 |
| **确定性** | Linux 非实时，偶发丢样 | 硬实时流水线，**实测零丢样** | 架构级 |
| **丢样可证明性** | 无法证明 | **Δin ≡ Δout 逐位相等** | 可审计 |
| **参数可见性** | 打印日志 | 3 条独立观测通道（串口 / GUI / JTAG） | — |
| **现场可重配** | 改代码 + 重启 Python | 串口命令，**实时生效** | — |
| **PL 资源** | — | 20 DSP48（25%）、4.5 BRAM（7.5%） | 低成本 |
| **时序** | — | WNS +0.540 ns，0 失败终点 | 收敛 |

### 时延对比的直观感受

| | 时延 | 相当于 |
|---|---|---|
| 软件转发 | 17 ms | 光在真空中走 **5100 km** |
| 硬件转发 | 81 ns | 光走 **24 m** |

对一个星地链路单向传播时延本就有 2~7 ms 的系统来说，**转发器自身从"引入 17 ms"变成"引入 0.000081 ms"**，这是一个数量级的差别。

## 六、方法论提炼

这次改造里有五条经验是可以迁移到其他项目的：

### ① 先算账，再动手

不要一上来就"优化代码"。
**先把需求量和供给量算成同一量纲，看看瓶颈到底在不在这段代码上。**

本例：需求 245.76 MB/s，供给 35 MB/s。
算完就知道：**再怎么优化软件，天花板也只有 4.37 MSPS。**
于是"改哪里"这个问题变成了一道算术题，而不是一道经验题。

### ② 区分"优化"和"改道"

- **优化**：在现有路径上跑得更快 → 受物理上限约束
- **改道**：让数据不再走那条路 → 上限消失

本例中，把 DDC/DUC 放进 PL 不是"让转发更快"，而是**让样点根本不进入那条 35 MB/s 的管子**。
改造后 USB 上的流量是 **0 字节**。

### ③ 最小可行实验优先做"最不确定"的那一步

项目最大的不确定性不是 DSP 算法，而是**"我能不能改 PL 而且板子还能起来"**。

所以第一步做的是 **三行 `assign` 直通**：
- 技术含量最低
- 但它一旦跑通，整个项目的风险等级就从"高"降到"中"
- 在它跑通之前，任何 DSP 设计都可能白做

**把风险最高、成本最低的那一步放在最前面。**

### ④ 验证体系要和设计同步建立，不能事后补

改造前"看频谱对不对"是**主观不可量化**的验证。
改造后"Δin ≡ Δout"是**可证伪**的验证。

**可证伪的判据**有四个特征：
1. 有明确的通过/失败阈值
2. 能被自动化
3. 坏消息不会被掩盖（丢一个样点就立刻不等）
4. 不依赖人的主观判断

本例中，这个判据直接来自 PL 里两个计数器——**验证能力是被"设计"进去的，不是事后附加的**。

### ⑤ 仿真验证的是 RTL，不是胶水代码

仿真是本项目发现两个真实 RTL 缺陷（NCO 复用错误、寄存器未复位）的唯一手段，**这两个缺陷读代码都发现不了**。

但同样要清醒：仿真覆盖不到 PS 侧的 C 代码。上机后仍然抓到一个"负数 double 转无符号是 UB"的 bug，导致**所有负频偏静默失效**——仿真里用的是自己算好的频率字，绕开了那个函数。

**仿真与上机验证是互补的，不能互相替代。**

## 七、遗留问题与后续

| 优先级 | 事项 | 说明 |
|---|---|---|
| P1 | SD 卡 `BOOT.bin` | 真正上电即工作，脱离 JTAG。当前受限于 bootgen 环境问题，需走 SDK 图形界面 |
| P1 | ILA 时钟改接 `data_clk` | 现在 ILA 抓的是异步域数据，波形混叠，无法用于诊断流水线时延 |
| P2 | CIC 抽取 + 信道 FIR | 从"宽带透明转发"升级到"窄带信道化转发"；剩余 60 个 DSP48 足够 2~3 个信道 |
| P2 | 闭环 AGC | 当前是手动增益 |
| P3 | 多普勒闭环 | 接口已就绪（`RELAY_DDC_FREQ` / `RELAY_DUC_FREQ` 可被外部算法实时写入），缺的是频率估计算法与统一时基 |
| P3 | 轻量 AXI DMA → GPU 感知面 | DDC 后仅 0.8 MB/s，Xilinx 自带 AXI DMA 即可 |

### 关于"星载载荷"定位的说明

本平台是**地面等效验证平台**，不是飞行件。要上星还需要：

- 抗辐照器件（当前是商用级 Zynq）
- 统一时基（GPSDO / 1PPS）—— 没有它，多普勒测量与遥测时间戳都不可审计
- 看门狗与失效保护策略
- 热设计与减振

但**架构本身是可迁移的**：三平面划分（数据面 / 感知面 / 控制面）、数据面 PL 内闭环、PS 只配置这三个原则，与器件等级无关。
